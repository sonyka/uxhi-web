05

Point the domain Go live

All yours, in order. No deploy needed — this is purely DNS.

  • Netlify — Domain management → Add a domain → uxhi.community. Decline any offer to manage the DNS or change nameservers
  • SiteGround DNS editor — set the apex @ to ALIAS → apex-loadbalancer.netlify.com, or A → 75.2.60.5 if ALIAS isn’t offered. Set its TTL to 300
  • SiteGround DNS editor — set www to CNAME → splendid-entremet-f6cb1d.netlify.app
  • Wait until uxhi.community stops answering with 34.174.88.19. Usually under an hour
  • Confirm HTTPS works. If it hasn’t after a few minutes: Netlify → Domain management → HTTPS → Verify DNS configuration → Provision certificate
  • Walk uxhi.community — homepage, About, the member directory and its filters, both Resources PDFs, the Join and contact forms, and that www lands in the same place
  • Check uxhiconference.com and its 2025 archive still load
  • Leave the SiteGround hosting active for a few weeks
  • A week later — set the apex TTL back to 14400

Don’t touch the MX or TXT records, and don’t move the nameservers. That is what would break email on the domain.

Launch readiness

audit · 7 Sep

What this is. A sweep for the things a public address exposes that a preview address does not — how the site is found, how it behaves for people who can’t use it the default way, and what happens when something goes wrong or someone abuses it. The four launch gates are in Path to launch. Nothing below holds the doors shut; it is ordered so the riskiest goes first.

  • Session B — soon after launch
  • ✓DevSpam protection on the three forms — 8 Sep. Correction to this audit: all three already had a honeypot, and a good one; the earlier finding was wrong. What did not work was the rate limit, which lived in memory and so was mostly imaginary on serverless. A stateless timing check replaces it, and the three drifted copies of the honeypot are one component
  • ✓DevError monitoring — 8 Sep. Errors now post to Slack, from the server and from the browser. Visitors get a real page with a reference code rather than a stack trace. Throttled, so one broken page cannot flood the channel
  • ✓DevSecurity headers — 8 Sep. Five of them, set in the app so staging gets them too. Framing is allow-listed rather than blocked outright, since a flat block would have quietly broken Sanity visual editing
  • Session C — first weeks
  • ✓DevReduce motion respected — 8 Sep. One setting at the root covers every animation on the site, so content still fades in but stops flying about. Verified with the setting actually switched on, not assumed
  • ✓DevImage sizing — 8 Sep. 67 of 92 fixed, including all the hero art: those were being sent as 1920px files for a slot that is never wider than 152px, and now arrive at 256px
  • ✓DevThe last 25 images — 8 Sep. Measured at three widths each rather than guessed, because a photo strip, a collage pill and a full-width banner are three sizes wearing the same markup. Every image on the site now declares its size, from none of 92
  • ✓DevSkip-to-content link — 8 Sep. First thing in the tab order, invisible until focused, and it moves focus into the content rather than only scrolling to it
  • ✓DevHome-screen icons — 7 Sep. Done alongside the favicon: an iPhone bookmark gets the UXHI mark instead of a screenshot
  • Once production is live
  • DevThe rest of the Content-Security-Policy. The header exists but only controls framing. A script-src is the part that actually stops cross-site scripting — and the part that silently breaks Next’s inline bootstrap, analytics and the Studio if written blind. Unblocked 8 Sep — production is now live, and this could not be tested honestly before it was: the development server uses eval for hot reloading, so a policy that passes locally proves nothing about the built site. The way in is report-only first — let the browser say what it would have blocked, walk the site and the Studio, then enforce what the reports prove
  • Submit the sitemap in Google Search Console, once the domain answers
  • Confirm the Slack error alerts arrive from the live site, not just that the setting exists
  • Watch analytics for a day and check the numbers look like people rather than bots
  • Session D — needs you, or can wait
  • Check Slack alerts arrive. Error monitoring posts to SLACK_WEBHOOK_URL, the same one the forms already use. If you get a Slack message when someone submits a membership application, this is already working and there is nothing to do. If not, that is the thing to check in Netlify. Optionally add SLACK_ALERT_WEBHOOK_URL for a separate alerts channel — the code prefers it
  • ✓Privacy notice — 8 Sep, at /privacy, linked from the footer. Written from what the code actually does, so it names the six services that genuinely receive anything. Removal goes through the contact form, since neither this site nor the current one has ever published an email address
  • ✓The children section came out of the privacy notice (8 Sep) — not required (the law binds sites aimed at under-13s or knowingly collecting from them, and this is neither) and written from an assumption about the audience rather than from anything the system does, which is the standard the rest of that page is held to
  • One thing in the privacy notice still wants your word. “Within 30 days” for removals is a number I chose. Someone on the board should also read the whole thing — it is written from the system, but it is not legal advice
  • DevNothing actually deletes form submissions after 90 days. The notice now promises it; today contact submissions sit in the CMS and in Slack indefinitely. Either someone clears them each quarter or it wants a scheduled job — a promise the code does not keep is worse than no promise
  • ✓DevHousekeeping — 8 Sep. Linter is at zero. The warnings turned out to be dead code rather than untidy imports: Events fetched its list from the CMS and rendered none of it (the listing is a Luma embed), and Resources did the same with the reports query. Starter graphics gone, Node version pinned

The directory becomes findable the moment the domain does. Today it is deliberately hidden from search engines because the preview addresses are not meant to be found. On the live address it will be indexed and cached by Google — 63 people’s names, photos, titles and LinkedIn profiles. That is presumably the point of a directory, but it is the sharp end of the consent question already open above, and it wants a line in the privacy policy.

Sound already, so nobody needs to spend time here. The rules that keep search engines away from the preview addresses are host-aware and genuinely well built. Analytics is gated so staging never pollutes the real reports. All three forms validate their input and check uploaded file types, and the Slack notification fails quietly rather than taking the form down with it. No credentials anywhere in the source. Every page has a title and description. The archive redirects for past conference years are carefully reasoned. Dependencies are current and there are only sixteen of them.
